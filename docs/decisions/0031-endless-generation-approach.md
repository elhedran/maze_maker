# Context

[DR-0007](/decisions/0007-wave-function-collapse.md) makes the world infinite and generated around the player, and says the team should research where new areas meet old ones. It lists contradiction handling, determinism and persistence as follow-ups. The [roadmap](/roadmap.md) gates slice 2.6 ("Beyond the edge") and the game on that research. Ian (`human:ian`, 2026-11-01) asked for concurrent work and for progress toward the game in a debug mode, so the research ran early, alongside 2.1.

The research is [Endless WFC](/plans/endless-wfc-research.md). Its answer: WFC can do it, with conditions, and replacing WFC (the roadmap's one-way door) is not needed. Slice 2.1's generator ([DR-0028](/decisions/0028-wfc-approach-for-2-1.md), `rowan/2.1-wfc` at 6097188) is the building block.

# Decision

1. **Chunks.** The world is a grid of S × S cell chunks, with S = 16 to start (a setting, the engineers' call). Cells have `i64` world coordinates.
2. **Border labels first.** Every cell edge on a chunk border is labelled *closed* (hedge on both sides) or *open* (passage or door on both sides), by a hash of (world seed, border key, position along the border). Room floor never crosses a border, so every room lies inside one chunk. One edge per border, chosen by a hash of (world seed, border key), is forced *open*: the **gate**. How often an edge is open is a tuning setting. **Border key:** each border has one canonical key, the coordinates of the chunk on its east or south side plus the axis (vertical or horizontal), so both neighbours hash exactly the same input. A test derives a border's labels from each side and compares them (Rowan).
3. **A chunk is a pure function** of (world seed, chunk coordinates, tile set, generator version). It is generated by DR-0028's WFC unchanged, except that border cells start with only the candidates that match their labels. Its seed mixes (world seed, chunk x, chunk y, attempt) through the SplitMix64 finaliser. No chunk ever reads another chunk's tiles, so the same chunk comes out the same in any visiting order.
4. **A way onward.** After generating, a flood fill checks the chunk's four gates are joined inside it. If they aren't, it regenerates with the next attempt seed, up to R times (a constant, engineers' call). After that, a path joining the gates (the **spine**) is chosen from the chunk seed, its edges are pinned *open*, and WFC fills around it. The fallback run (rule 5) always carries the spine, so the guarantee holds there too. Every chunk joins its gates and gates are shared, so the gate network is connected and endless. The player spawns on it. This answers Q-0008's must-have as a guarantee.
5. **Contradictions and the attempt order.** DR-0028's restarts with the full tile set (up to 20). If all of them fail, one run with corridor and hedge tiles only, with the spine pinned, which can't contradict (rule 6) and needs no gate check. A chunk is never left unfinished. Attempts run in this fixed order, and one attempt counter runs across all of them and goes into the seed (Rowan's proposal):
   1. gate tries 0 to R, full tile set, no spine, each with up to 20 contradiction restarts; the first run that completes and passes the gate check is the chunk;
   2. then the spine with the full tile set, up to 20 restarts;
   3. then the fallback: corridor and hedge only, spine pinned, one run.

   The worst case is (R + 1) × 21 + 22 runs, about 100 at R = 3. The result reports the attempt count, whether the spine was pinned and whether the fallback ran.
6. **The completeness invariant, checked on the table.** For each of the 16 combinations of hedge and passage on a cell's four sides, the tile set must have a variant that fits (the core set has hedge, 4 dead ends, 4 corners, 2 straights, 4 Ts and 1 crossroads). And for those 16 variants, in every direction, every pair whose facing sides are both hedge or both passage must have a **table entry weight** above 0: the weight the solver's support reads (DR-0028 rule 1), so bases, tile weights, exception multipliers and noise are all covered. Tile weights alone aren't enough: a `passage_passage` or `hedge_hedge` base of 0, or a zero straight-to-straight multiplier, would break the fallback proof (Rowan). `maze-core` checks this when the tile set loads, as an error.
7. **No persistence for generation.** Chunks are cached near the player and regenerated on demand. When the game saves a world, it stores the world seed, a fingerprint of the tile set and generator version, and any changes the player made. How the game handles a mismatched fingerprint is the game's decision, not this one.
8. **Slice 2.6 is the experiment**, with the measures and the definition of done in the research note: order independence and the way onward as tests, plus the fallback rate, restarts and spines, seam statistics, room sizes, time per chunk (median, 99th percentile and the worst case of about 100 runs), and review of seams by Wren and Damson. Chunks are generated ahead of the player, off the UI thread.

## Why it's a two-way door

Nothing is built on it yet, and nothing is saved. The chunk generator is a layer over DR-0028's solver, and the solver doesn't change. Moving to layered blocks (the fallback plan) reuses the same solver with constraints set differently, and throws away only the label and gate code. **It stops being two-way when the game first saves a world it promises to reproduce:** from then on, changing the rules above, the hashes, or the tile set changes worlds under existing saves. Yew re-checks this before that happens ([DR-0018](/decisions/0018-one-way-doors-go-to-ian.md)).

# Alternatives considered

- **One growing wave with backtracking** (Marian Kleineberg's infinite city[^marian42]). Order-dependent, has to keep everything it generates, and backtracking can change cells the player has seen. He dropped chunks because a finished chunk could leave its neighbour with no solution, which is exactly what rule 2 prevents.
- **Chunks constrained by their already-generated neighbours, with a border band regenerated on failure.** Rooms cross borders, but the result depends on visiting order, so it has to be stored, and the band's own borders can fail.
- **Layered modifying in blocks** (Boris the Brave[^boris-mib], after Merrell). Order-independent with no storage, and rooms can cross block borders. About four times the work (12 earlier blocks per final block), it needs a fallback background layer to be robust, and it is more code. Kept as the plan if 2.6 finds seams or the room cap unacceptable.
- **Full nested WFC with a second WFC as the outer layer** (Nie et al.[^nwfc]). More than this maze needs: the outer layer here is a hash. A coarse feature or zone layer may come later, and it would sit in that place.
- **Replacing WFC.** Not needed. It would be a one-way door for Ian.

# Consequences

- 2.6 no longer waits on persistence: generation doesn't need it. The roadmap's "Waits on persistence" for 2.6 can be dropped (Marram's call).
- Rooms are at most S × S, which caps Q-0008's "rooms growing without end". Rooms never straddle a chunk border. Whether that is felt is for review.
- Borders may be visible if label statistics differ from the interior. 2.6 measures this, and the tuning options are recorded in the research note.
- Rule 6 constrains future tile sets: Wren can't drop a corridor fallback to weight 0 without breaking the guarantee. The load check makes that loud.
- Zones ([DR-0022](/decisions/0022-weight-model.md)) fit as a weight set per chunk: border labels don't depend on zones, so zones still meet cleanly.
- The 2.1 single-maze path and DR-0028 are unchanged.

# Concerns raised

- **Yew (`architect/1`), the author:** the seam labels are coin flips that know nothing of the table, so borders may read as a faint grid of hedge and corridor stubs. If 2.6's review sees that, the first fix is a cheap one (a chain along the border tuned to interior densities), before anything bigger.
- **Rowan (`engineer-rowan/1`), approving.** Buildable as written. I checked it against `data/tile-sets/core.toml`, `side.rs`, `table.rs` and `wfc.rs` on `rowan/2.1-wfc`. Three notes need writing into the rules before 2.6 builds them, and two are smaller:
  1. **Rule 6 checks the wrong thing as worded.** The solver's support is `table.entry(d, c, n).weight > 0` (DR-0028 rule 1), and that weight is base × both tile weights × exception multiplier × noise. Noise can't reach 0 (amount < 1), but the loader accepts a base of 0 and a multiplier of 0. Set `passage_passage` or `hedge_hedge` to 0, or set the "Long straights are rarer than turns" multiplier to 0, and the fallback can contradict while every tile weight is still above 0. For example, a column of cells pinned passage north and south can only hold straights, and straight can't meet straight. So the edges are no longer independent and the proof fails. The load check must be: for the 16 corridor-and-hedge variants, every pair whose facing sides are both hedge or both passage has a table entry weight above 0, in every direction. That is the condition the proof needs, it reads the table the solver uses, and it's no harder to write. Zero-weight candidates being dropped (rule 1) doesn't break the proof, because this check covers it. Otherwise the proof holds: the 16 combinations are hedge, 4 dead ends, 4 corners, 2 straights, 4 Ts and 1 crossroads. Masks from labels and pins are product sets over edges, and `restrict` keeps them product sets.
  2. **The fallback must carry the spine.** A corridor-and-hedge run with no pinned path can leave the gates apart, which breaks rule 4's guarantee. The fallback run should always pin a spine (it can't contradict, because the spine only pins *open*), and then the gate check isn't needed after it.
  3. **Fix the attempt order, so seeds are deterministic.** Say how rule 4's R regenerations and rule 5's 20 restarts nest, and number attempts across both. My proposal: gate attempts 0..R, each with up to 20 contradiction restarts; then the spine with the full set and 20 restarts; then the fallback with the spine. The attempt number goes into the seed in that order.
  4. Smaller: edge and gate hashes need a canonical key for each border, for example the chunk on the east or south side plus the axis, so both neighbours hash the same input. One test should generate a chunk's labels from each side and compare them.
  5. Smaller, time: one 16 × 16 run is about 256 collapses over 29 variants. `restrict` costs at most 29 × 29 per call, so I estimate 1 to 3 ms in a release build, and the 10 ms median is realistic. I haven't measured it. The worst case is (R + 1) × 21 + 22 runs, about 100 at R = 3, which is a visible hitch. Measure 7 should report the median, the 99th percentile and the worst case. Chunks should be generated ahead of the player and off the UI thread.

  Per-cell masks fit `Wave::new` cleanly. It takes a starting mask of cells × variants and ANDs it with the zero-weight row. `run` already fails on a count of 0 and propagates every cell first, so the masks spread with no other change. `Generation.cells` can become `Vec<usize>` for chunks, since they never fail. I agree it's a two-way door until the first saved world.
- **Yew (`architect/1`), after Rowan's review:** notes 1 to 5 are written into rules 2, 4, 5, 6 and 8 as Rowan proposed them, and the research note is updated to match.

# AI guidance

- Never let generation read another chunk's tiles. A chunk depends only on hashes of the world seed and coordinates, the tile set and the code.
- Never let room floor cross a chunk border. Border edges are hedge on both sides, or passage or door on both sides.
- Run the completeness check on table entries, not tile weights. Don't weaken it (rule 6) to get a tile set to load. Raise it with Wren and Yew.
- Number attempts in rule 5's order and put the count in the seed. Changing the order changes every world.
- Hash border labels and gates from the border's canonical key (rule 2), never from the chunk being generated.
- Seeds and hashes are written out in `maze-core` (SplitMix64 and its finaliser), never `std` hashers or the `rand` crate (DR-0028 rule 5).
- Don't add storage of generated chunks to make something work. If something seems to need it, that is a sign order independence broke.
